# Repository Guidelines

## Project Structure & Module Organization
Protocol Studio uses Rust, Vue 3, TypeScript, and PostgreSQL. Backend modules live in `src/`; Platform/project migrations and security policies live in `migrations/platform/` and `migrations/project/`; root migrations are legacy split inputs. Frontend pages, components, and domain helpers live under `frontend/src/`. Tests are in `tests/` and `frontend/*-check.mjs`. Each `config/<project>/` contains a manifest, board table definitions, and optional sources or project Dump. Tooling and documentation live in `scripts/` and `docs/`.

## Build, Test, and Development Commands
- `./scripts/init-db.sh`: initialize local PostgreSQL 18 and apply migrations; creates no projects.
- `./scripts/create-project.sh dc-ups`: create from `config/dc-ups/`; repeated execution preserves data.
- `./scripts/dev.sh`: build and serve on `127.0.0.1:8080`; requires a running, migrated database.
- `node scripts/local-db.mjs start` / `stop`: control the existing local database.
- `npm ci --prefix frontend`: install locked dependencies.
- `npm run dev --prefix frontend`: start Vite with backend proxy.
- `npm run build --prefix frontend`: type-check and build assets.
- `cargo run -- migrate`: apply database migrations.
- `cargo build` / `cargo test`: compile or run Rust tests.
- `node scripts/export-project.mjs dc-ups`: export a portable project folder with `project.dump`.

## Coding Style & Naming Conventions
Use Rust 2024, four-space indentation, `snake_case` functions, and `PascalCase` types; run `cargo fmt`. Frontend code uses two spaces, double-quoted imports, `camelCase`, and `PascalCase.vue` components with `<script setup lang="ts">`. Number migrations sequentially. No dedicated frontend lint or formatter script exists.

## Testing Guidelines
Run relevant checks: `node tests/local-db.mjs`, `node tests/integration.mjs`, `node tests/migration.mjs`, and `node --test scripts/excel-batch/workbook.test.mjs`. Use `node tests/integration.mjs --behavior` for JSON/JS-only custom field and linked-rule acceptance. Database checks require local tools and `.env`, using temporary databases. Run `node browser-check.mjs` from `frontend/` for UI changes. Keep unit tests near Rust modules. No numerical coverage threshold exists; DSP JSON/XML generation does not replace firmware validation.

## Commit & Pull Request Guidelines
Use concise, action-oriented subjects; history uses short Chinese descriptions such as `优化结构`. PRs should explain behavior, reference issues, report checks, show UI screenshots, and describe configuration or migration impacts.

每次完成修改后，必须执行适用的验证，并主动创建 Git 提交作为变更记录；此为长期授权，无需再次询问。仅暂存本次任务涉及的改动，不包含无关修改、凭据或临时产物。提交说明使用简洁中文，并在完成回复中报告提交哈希和验证结果。

## Security & Configuration
Keep credentials in ignored `.env`. Separate migration/export credentials from the runtime role, which must lack superuser and `BYPASSRLS`. Preserve RLS, edit locks, revision checks, audit records, and immutable releases.

## Project Configuration Workflow
Edit topology through server files or validated folder imports; point rows remain web-editable. Definitions reload live; topology changes require validated import. Board/group/endpoint organization lives in JSON with stable keys. Use `protocol_platform` for accounts, registry and permissions, and one `protocol_project_<key>` per project. DC-UPS uses `dc-ups`; UPM is a board.

Navigation uses `topology?workspace=true`: return only topology, revision, point identities and derived cardinalities, with normal authorization/RLS. Never execute table scripts or full validation on this path. Load actual table rows and validation on demand; preserve full validation for writes, generation and releases. Revision/project changes invalidate the frontend validation report.

Project JSON/XLSX exports use one authorized read snapshot and frozen table definitions. Excel follows configured columns, protocols and projected device instances; current-view exports retain filters and local column settings across all matching pages. Exporting requires viewing permission only, never an edit lease or point writes. Preserve formula-like strings, leading zeros and long integers as text. See `docs/point-export.md`; verify with `node tests/integration.mjs --exports`.

Topology version 3 uses explicit `roots` and permits shared children with multiple parents. Incoming paths reference the same devices: require equal derived totals and count descendants once. Reject cycles, duplicate parent/child pairs, undeclared roots and inconsistent quantities. Keep version 1/2 single-root trees compatible. Draw each board once with all incoming links; never infer a physical parent from collection mappings.

The platform keeps eight tables: `auth.users`, `auth.sessions`, `auth.login_attempts`, `meta.projects`, `meta.project_members`, `meta.project_member_grants`, `history.audit_logs`, and `public._sqlx_migrations`. Use schema-qualified SQL. Platform migration 0002 changes grouping only; preserve records, constraints, sessions and authorization locks. Platform migration versions are independent of each project's `schema_version` and `revision`.

Each project has eight tables: `points.process_points`, `points.collect_points`, `points.transmit_points`, `history.events`, `history.releases`, `meta.project_state`, `meta.previews`, and `public._sqlx_migrations`. Events distinguish point/audit/import records; state includes the editing lease. Scope previews by kind, project and creator. Verify registry/state UUIDs and hold authorization locks through business commits. Folder imports preserve points without Dump; Dump replaces only current points and preserves history. Export version `(7,4)` includes three point tables, accepts `(6,3)` archives and legacy `(4,1)` / `(5,2)` two-table archives with empty collection data. Preserve recovery journals and project isolation; use one server per configuration directory.

DSP internal data follows the `DSP内部数据` worksheet and has no sigID. Preserve its 25 source fields, with communication type and model hidden from the internal table. Keep system IDs hidden for stable transmit references. Preserve original variable spelling, `Sys_` types and source cells; edit metadata through individual whitelisted fields. Communication type is a suggestion, edited only per transmit mapping with override warnings and conversion validation. DSP UPP models are fixed by internal category and read-only in the transmit table; changing category updates every linked mapping atomically, with permissions, address checks, previews and history. DSP transmit names inherit the current internal name; every existing mapping participates in validation and generation, including legacy disabled rows. Do not expose independent DSP transmit name/enabled/conversion/byte_order inputs; derive conversion from internal and wire types and normalize the DSP byte-order compatibility value to 0. Retain shared storage fields for compatibility with other boards and Dumps. Keep UPM receiver settings independent from DSP. Show protocol byte count from wire_length. Never silently rewrite existing wire types or addresses. Keep each board's definitions and communication configuration independent.

Board organization and common capabilities are selected by JSON, group `collect_enabled`, endpoint protocol/direction and `workbook_import`; never branch on board/model names. Put table-specific normalization, projection, validation and linked updates in board-local JS referenced by each table's `behavior`. Declare custom input, metadata, display and owned fields explicitly; protect IDs, associations and source evidence. Keep storage, authorization, revision merging, history and protocol safety in Rust. Frontend display uses table `fields` and `presentation`; no board-specific component dispatch. Use `import-board <project> <board>` for additive initialization (`import-upm` remains an alias). XLSX mappings live in each board’s `workbook.json`; freeze mappings and applied definitions/scripts in previews. Previous board-specific importers are test-only regression references. See `docs/board-configuration.md` and `docs/table-behavior.md`.

DSP process and transmit behavior use `export function behavior(context, parameters)` for `normalize`, `project`, `reconcile` and `validate`. Custom fields persist only through whitelisted metadata; scripts return every existing row exactly once for projection/reconciliation. Script failures roll back the whole change, including linked rows. Reads do not persist calculated values. Freeze scripts and parameters in previews and generated releases. New projects reusing existing point/protocol/UI contracts should need only JSON/JS; genuinely new protocol encodings or storage capabilities still require common engine work.

DSP transmit `calculation` references the same bounded `transmit.js` file through `script_file`, with a separate `export default function calculate(points, parameters)` entry point. The Rust JSON `builtin` engine remains supported for compatible layouts. Only `id`, `address` and `wire_length` may be returned, for every existing mapping exactly once. Recalculate after a full single/batch change, before permission/validation/history checks; keep UI display order and previous computed values out of script inputs. Freeze both parameters and script contents in previews and reject changed scripts at commit. Configuration reads and imports without Dump never rewrite points. Require explicit reviewed recalculation when imported/stored layouts differ; block generation until synchronized. Keep manual wire types and scales independent; do not expose calculation-owned address/length editors. See `docs/table-calculation.md`.

UPM uses LOCAL and DSP templates with independent device instances in JSON. LOCAL has no collection mappings; eight DSP instances share one point definition and have independent dev_id and stable zero-based instance_index values. UPM transmit instance_calculation runs the same behavior JS with action instances; its JSON parameters define template_base/device_stride and JS calculates index * stride + template base + point offset. Reuse the calculated instances for display, overlap/range validation, generation and derived collectors; legacy boards without the flag retain modbus_base compatibility. Import UPM from its local/DSP/CSU worksheets, excluding CSU-local rows. Preserve missing sigIDs and source warnings; merge equal local enums only when internal definitions match, retaining multiple transmit mappings. UPP addresses count bytes; Modbus addresses count registers. Use `import-upm <key>` only for additive first-time initialization; existing UPM data is preserved. See `docs/upm.md`.

UPM collection Base 地址 persists as whitelisted metadata.base_address, independent from its UPP address. With source_tables, scripts receive readonly collections/transmissions/endpoints on each source. linked_fields may update only forward address when no calculation exists; keep all resulting writes inside normal permissions, preview, merge and history checks. Unset collection bases display the current unique Modbus offset without writing it; explicit values synchronize linked Modbus rows. Clearing a base removes the link and preserves the last offset. Never infer Modbus offsets from UPP byte addresses or rewrite existing rows on configuration reads. Test with `node tests/integration.mjs --upm-address`.

Collection endpoint `subset_of: {board_key, endpoint_key}` declares a JSON-only source relationship to another native board’s compatible transmit endpoint. Validate unique membership by model/address/type/length/scale/access. After a complete point change and layout recalculation, follow the pre-change source record ID and synchronize existing collectors before permissions, previews, revision merge checks and history. Preserve receiver polling, priorities, byte order and internal definitions; never add unselected source rows automatically. Reject deletion of referenced sources, ambiguous matches and incompatible receiver storage atomically. Configuration reads and imports without Dump never synchronize or rewrite points; imported layouts must pass subset validation. No board-name dispatch or extra database table is required.

Derived devices use JSON `point_storage: "derived"` and exactly one Modbus collection endpoint. Their readonly `collect.json.mapping` references a native board's transmit endpoint and one bounded board-local JS file. Expand every source/device pair exactly once; only source_id/device_code/address/dev_id are script outputs. Inherit source names, types, lengths, register areas, scale and access; receiver parameters live in JSON. Never store derived point copies or allow point-write APIs. Reuse the bounded QuickJS runtime; validate coverage, source identity, ranges and overlap, surface runtime errors and block generation/releases. Generated collection files freeze script contents and rows. See `docs/upm-demo.md`.
